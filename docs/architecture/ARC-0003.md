# ARC-0003 — Actionables surface the full lifecycle, with an editable/auditable email preview and manual enrichment fallback

- **Status:** Accepted (architect-ratified)
- **Owner:** @architect
- **Applies to:** the Actionables View, Rendering, Sent Record, and Enrichment
  concepts (see ARC-0001 for the base pipeline these extend), and their
  callers
- **Supersedes:** —

## Concepts

| Concept | Role |
|---|---|
| **Actionables View** | The dashboard's default row listing. Decides which rows the human sees as "still needs me," across the *whole* lifecycle — not just the pre-send states. |
| **Rendering** *(ARC-0001, extended here)* | Turns a row + template into an email a human can preview and edit before it's sent. |
| **Sent Record** | An immutable snapshot of exactly what was sent (subject, body, timestamp) for a row, kept distinct from the still-editable draft. |
| **Enrichment** *(ARC-0001, extended here)* | Looks up missing details (HR email, company) for a row. When it can't find one, the human can supply it directly — enrichment never dead-ends the row. |

  ACTIONABLES VIEW — which rows does the dashboard show by default?

    row.status

    Is status one of: offer, rejected, skipped?

        │          (still reachable via an explicit filter/archive view).
        └─ no  ─▶ ACTIONABLE. Shown by default — this includes
                   needs_info, ready, sent, awaiting_hr_reply,
                   interview_scheduled (any round), and failed.
                   A row does NOT disappear on send; sending is one
                   step in the middle of the lifecycle, not the end.
```

  PREVIEW / EDIT / SEND — draft vs. sent record

  Rendering builds a draft from   Human edits the draft in the
  row + template                 preview UI (subject + body)
        │                                    │
        └─────────────────┬──────────────────┘
                           ▼
                  draft (row.final_subject /
                  row.final_body) — mutable,

  The dashboard must be able to show BOTH: the live/editable draft
  (for the next action) and the Sent Record (for "what did I actually
  send," e.g. after an HR reply arrives and the human wants to recall
  the original email).
```

```text
  LIFECYCLE PROGRESS UI — variable-length timeline, not a fixed N-step stepper

  A row's lifecycle has a variable number of events (interview rounds can
  repeat 0, 1, 2, 3+ times) — a fixed "step 1 of 4" indicator would either
  under-represent repeated rounds or force a fake cap. Render it as a
  timeline of entries instead, oldest first:

    ● Applied            (application notice ingested)
    ● Sent                sent_at
    ● HR replied           hr_reply classified, thread matched
    ● Interview — Round 1  scheduled_at (if known)
    ● Interview — Round 2  another HR reply advanced the round
    ○ Outcome              pending — no offer/rejected transition yet

  Rules for rendering a row's timeline:
    - One entry per lifecycle event actually recorded for the row (per the
      Lifecycle State Machine's transitions, ARC-0001) — never a
      pre-allocated fixed set of slots.
    - Every "Interview — Round N" entry is its own timeline entry, labeled
      with its round number — consistent with ARC-0001 invariant 8
      (round is a counter, not a new status per round).
    - The last entry reflects the row's current status; it is "pending"
      (open circle) until a terminal status (offer/rejected/skipped) is
      reached, then shows that outcome (closed circle).
    - This is the only place a row's history is rendered as a sequence —
      it must be derived from the row's stored lifecycle timestamps/round
      counter, not hand-maintained separately from them.
```

```text
  ENRICHMENT FALLBACK — HR email / company unknown

      Scraper enrichment (scraper.py) run for this row
        ├─ found a value ─▶ pre-filled, still human-editable
        └─ found nothing ─▶ field left blank, row stays needs_info —
             human is shown an editable field in the Actionables UI
             and can type the HR email / company directly.
             A manually-entered value is marked hr_email_source =
             "manual" (existing convention) and is never overwritten
             by a later automated scrape.
```

## Context

The dashboard's queue listing currently defaults to `[STATUS_NEEDS_INFO,
STATUS_READY]` (`app.py`'s `api_list_queue`), so the moment a row moves to
`STATUS_SENT` it silently drops out of the default view the human works
from. ARC-0001 already established that a job application has a full
lifecycle — applied → sent → HR reply → interview round(s) → offer/rejected
— and that the Lifecycle State Machine (`lifecycle.py`, still a stub) is
where those transitions get validated. But nothing before this ADR said
*what the human should still see* while a row is mid-lifecycle. In practice
that means a candidate is invisible in the UI for every step after the
first send — exactly the steps (HR replies, interview scheduling,
outcome) the architect most wants visibility into.

Separately, the app already has the pieces of a preview/edit flow
(`api_preview`, `api_finalize` writing `final_subject`/`final_body`,
`api_send` using them if present) but no record of what was *actually*
transmitted once a row's draft is later edited or reused, and no exposed
"here's the example vs. here's what went out" distinction. And while
`api_patch_queue_row` already lets a human manually set `hr_email`, it
doesn't cover `company` — so a row Enrichment can't resolve still has no
path to becoming actionable other than editing the database by hand.

## Decision

1. **Actionables View is lifecycle-wide, not pre-send-only:** the
   dashboard's default row listing includes every row whose status is not
   terminal. Terminal = `offer`, `rejected`, `skipped` (a human closed the
   row deliberately). Every other status — including `sent`, `failed`, and
   every future post-send lifecycle status the Lifecycle State Machine
   introduces (`awaiting_hr_reply`, `interview_scheduled` at any round) —
   remains in the default Actionables View. A row must never disappear from
   it purely because a send happened.
2. **Terminal rows stay reachable, just not default:** rows in a terminal
   status are not deleted and must remain queryable (e.g. via an explicit
   status filter or archive view) — invariant 1 only governs the *default*
   view.
3. **The UI must expose lifecycle progress per row, as a variable-length
   timeline:** wherever a row is shown in the Actionables View, the human
   must be able to see where it currently sits in the lifecycle as a
   timeline of the events actually recorded for that row (applied → sent →
   HR replied → Interview Round N, repeated as needed → outcome) — not a
   fixed-step indicator that assumes a constant number of stages, and not
   just a flat status string with no sense of progression. See the
   "Lifecycle Progress UI" diagram above for the rendering rules.
4. **Preview is always available before send, and is editable:** any row
   with enough data to render (see `build_template_context`) must let the
   human generate a preview (subject + body) before sending, and edit that
   preview's subject/body prior to send. This is the existing
   preview/finalize flow (`api_preview`, `api_finalize`) — this ADR ratifies
   it as required, not optional, for every send path.
5. **A Sent Record is captured at send time and is immutable:** the instant
   `api_send` transmits a row's email, the exact subject/body/timestamp that
   went out must be captured as a Sent Record distinct from the row's
   editable draft (`final_subject`/`final_body`). Later edits to the draft
   (e.g. preparing a follow-up) must never retroactively change a
   previously-captured Sent Record.
6. **Both draft and Sent Record must be viewable in the UI:** the human must
   be able to see, for any row that has been sent, both (a) the current
   editable draft and (b) the historical Sent Record(s) of what was actually
   transmitted — so "what did I preview" and "what did I actually send" are
   never conflated.
7. **Manual enrichment fallback, for every enrichable field:** when
   automated Enrichment (`scraper.py`) cannot resolve a field needed to
   send — HR email or company — the Actionables UI must let the human type
   the value directly, the same way `hr_email` can already be patched
   manually. A manually-supplied value is marked with source `manual` and
   is never silently overwritten by a later automated scrape.

## Rationale

The send-gate and lifecycle work ARC-0001 ratified only matters if the
human can actually see and act on a row through every stage that requires
them — a correct state machine that's invisible in the UI is no better than
no state machine. Making the Actionables View lifecycle-wide instead of
pre-send-only fixes the exact failure the architect flagged: applications
silently going dark in the dashboard right when they start needing
attention (an HR reply, an interview to schedule). Splitting "draft" from
"Sent Record" avoids a subtler failure mode: without an immutable
snapshot, "what did I send" becomes reconstructable only by rendering the
current row again — which silently lies once the row has been edited
since. And extending manual override to every enrichable field (not just
`hr_email`) means a scrape failure is a form field to fill in, not a dead
end requiring direct database access.

## Consequences

- `app.py`'s `api_list_queue` default (`[STATUS_NEEDS_INFO, STATUS_READY]`)
  must change to "everything not terminal," per invariant 1 — this is a
  behavior change from the current code, not a re-statement of it.
- The Persistence Gateway's schema needs a place to store one-or-more Sent
  Records per row (e.g. a `sent_emails` table keyed by queue row, separate
  from `queue.final_subject`/`final_body`) — schema migration, not covered
  by this ADR.
- `PatchBody` (`app.py`) needs a `company` field (and any other
  Enrichment-sourced field the UI exposes) alongside the existing
  `hr_email`/`hr_name`, following the same manual-source convention.
- The frontend queue UI needs a per-row timeline component per invariant 3
  (not a fixed-step stepper), driven off the row's stored lifecycle
  timestamps/round counter, plus a preview/edit surface that can show both
  the live draft and past Sent Record(s) — the timeline's rendering rules
  are specified above; visual styling is not.
- Once the Lifecycle State Machine (`lifecycle.py`, ARC-0001) is
  implemented, its status vocabulary is what invariant 1's "not terminal"
  check must be evaluated against — this ADR does not itself define the
  full status list.

## Open (not yet ratified — do not implement past this line without a decision)

- Whether a row keeps one Sent Record per send attempt (e.g. an initial
  send plus a later follow-up) or only the most recent is undecided —
  invariant 5 only requires that each capture, once made, is immutable.
- Whether `failed` rows auto-retry or require an explicit human resend
  action is undecided (ARC-0001 already leaves auto-retry-and-send
  unratified; this ADR doesn't reopen that).

architect sign-off — a developer or agent request alone does **not** authorize it.
