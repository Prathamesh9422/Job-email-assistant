# ARC-0004 — Browser-plugin applied-job ingestion with dedup

- **Status:** Accepted (architect-ratified)
- **Owner:** @architect
- **Applies to:** the new Browser Ingestion Path (browser extension → API →
  Persistence Gateway) described below, and its callers
- **Supersedes:** — (extends ARC-0001; does not replace it)

## Context

Not every applied job produces a Gmail notification the existing Ingestion
Path (`fetch_job.py`) can pick up — some applications are only visible on
the job site's own "My Applications" / application-history page. To close
that gap, a browser extension will open that page, scrape the list of
applied jobs, and call an API in this application so those applications get
recorded and can later be enriched with an HR contact for the reply-email
flow, the same as any other row.

This introduces a second, independent way for a `queue` row to come into
existence — today every row requires a unique `gmail_message_id`, which a
scraped row will never have. It also introduces a dedup problem: the same
applied job could get scraped more than once (re-running the plugin,
re-opening the page), and must not create duplicate rows or clobber a row
that already exists from the Gmail path.

## Decision

1. **New Ingestion Path variant, same invariants:** the browser
   plugin → API path is a Browser Ingestion Path under ARC-0001's Ingestion
   Path concept. It may scrape, parse, and write rows via the Persistence
   Gateway — it must never enrich, render, or send (ARC-0001 invariants 1,
   4, 10 apply unchanged, regardless of the human having manually opened
   the browser tab).
2. **Single entry point:** `browser_ingest.py` is the only component that
   accepts scraped applied-job payloads and turns them into
   Persistence-Gateway calls. The API route in `app.py` is a thin
   pass-through to it — no scraping-payload parsing or dedup logic lives in
   the route handler itself.
3. **Shared table, tagged source:** scraped rows live in the same `queue`
   table as email-sourced rows (not a separate table). `gmail_message_id`
   becomes nullable; every row gains a `source` column
   (`'gmail' | 'naukri_plugin'`) so the two origins stay distinguishable
   without ever being merged or conflated.
4. **Dedup key:** a scraped row's identity is
   `hash(company + role_title + applied_date)`, scoped per user. This is a
   fallback key (no stable per-application id is assumed to be scrapable
   from the page) — it will collide if the same user applies to the same
   role at the same company twice on the same day; that is accepted, not
   solved, by this ADR (see Open).
5. **Insert-or-skip, never overwrite:** a dedup match means the incoming
   scrape is discarded — the existing row's fields are never overwritten by
   a later scrape of the same application, regardless of which source
   (`gmail` or `naukri_plugin`) created it first. This mirrors the existing
   `INSERT OR IGNORE` / `ON CONFLICT DO NOTHING` pattern already used for
   `gmail_message_id` in `insert_queue_row`.
6. **New rows start at `needs_info` with no HR contact:** a scraped row is
   inserted with `status = needs_info` and `hr_email_source = none`,
   exactly like a freshly-parsed application-notice row — it enters the
   existing human-triggered Enrichment step (ARC-0001) the same way, with
   no special-cased enrichment path for plugin-sourced rows.

## Rationale

Reusing the existing `queue` table and its lifecycle/enrichment machinery
(instead of a parallel table merged in later) means a scraped row is a
normal row from the moment it exists — it shows up in the same dashboard,
goes through the same Enrichment and Review & Approval Path, and is bound
by the same send-gate, with no special-cased "external" row type for the
rest of the pipeline to account for. Tagging `source` rather than silently
mixing origins keeps it possible to answer "did this come from Gmail or the
plugin" later without guessing.

A single entry point (`browser_ingest.py`) for turning scraped payloads
into rows keeps the dedup rule in one place — the same reasoning ARC-0001
already applies to the Gmail Gateway and Persistence Gateway: one place to
audit, not logic re-implemented per caller.

## Consequences

- Schema migration required: `gmail_message_id` becomes nullable, and
  `source` (+ a dedup key column or a generated/stored hash) is added to
  `queue`. This ADR requires that migration exist; it does not specify its
  exact SQL.
- `insert_queue_row` (or a sibling function alongside it) must grow a
  scraped-row path that dedups on `(user_id, source, company, role,
  applied_date)` instead of `gmail_message_id` — today it hard-requires
  `gmail_message_id`, which is a gap this ADR flags, not one it closes (see
  the code-vs-ADR gap noted below).
- The dashboard/list views that currently assume every row has a
  `gmail_message_id` must tolerate rows where it's null.
- Callers must not add a second way to insert scraped rows outside
  `browser_ingest.py` — extending the plugin (new fields, new source site)
  means extending that module, not adding a parallel path in `app.py` or
  elsewhere.

## Open (not yet ratified — do not implement past this line without a decision)

- The `(company + role + applied_date)` hash collision case (same role,
  same company, same day, applied twice) is accepted as a known gap, not
  solved — no decision here on whether to add a disambiguating field later.
- The exact scraped payload shape the browser plugin sends to the API
  (field names, batch vs. one-row-per-call) is not specified here.
- Whether/how a scraped row's `applied_date` reconciles with a later
  Gmail-sourced notification for the *same* application (i.e., whether they
  ever get merged after the fact rather than staying two dedup'd-apart
  rows) is undecided.
- ~~Authentication of the browser plugin's API calls~~ — **Resolved:** a
  per-user long-lived API token (`users.api_token_hash`, generated from the
  dashboard, sent as `Authorization: Bearer`), not the session cookie — a
  `chrome-extension://` origin can't reliably rely on `SameSite=Lax` cookies
  for a cross-site call. See `auth.py`'s ARC-0004 invariant 4 and
  `require_user_or_token()`. Only the token's hash is ever persisted.

## Change process

This decision is ratified. Any change to the invariants above requires updating this ADR and
architect sign-off — a developer or agent request alone does **not** authorize it.
