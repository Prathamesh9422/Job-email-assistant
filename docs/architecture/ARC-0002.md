# ARC-0002 — Sign-in-with-Google identity replaces hardcoded credentials

- **Status:** Accepted (architect-ratified)
- **Owner:** @architect
- **Applies to:** the Sign-In Flow, Credential Store, Gmail Gateway, Ingestion
  Path, Persistence Gateway, and Review & Approval Path concepts (see
  ARC-0001 for the base concepts this one extends), and their callers
- **Supersedes:** the single hardcoded-credential assumption in ARC-0001's
  Context and in `PRODUCTION.md` ("restricted scopes, single user," static
  `GOOGLE_CLIENT_ID`/`SECRET`/`REFRESH_TOKEN` env vars) — ARC-0001's other
  invariants (send-gate, gateway boundaries, lifecycle) are unchanged, now
  applied per user instead of globally

## Concepts

| Concept | Role |
|---|---|
| **Sign-In Flow** | The Google OAuth consent + callback exchange that authenticates one user and yields their credential. The *only* path by which a Google identity enters the system. |
| **Session** | Ties one authenticated dashboard visit to exactly one user identity. Every request on the Review & Approval Path runs in a session. |
| **Credential Store** | Where a signed-in user's OAuth token (refresh token) is persisted, keyed to that user — not a file, not an env var. |
| **User Scope** | The partition key (owning user identity) applied to every row and every Gmail Gateway call from this point on. |

## Context

The app currently authenticates to Gmail one of two hardcoded ways: locally,
a one-time interactive consent that writes a token file to disk; in
production, a single static `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`/
`GOOGLE_REFRESH_TOKEN` triple set as Railway environment variables
(`PRODUCTION.md` step 1). Either way there is exactly one Gmail identity
baked into the deployment, and every scrape, every row, and every send
implicitly belongs to that one account.

The architect wants this to become a real "Sign in with Google" experience:
any user opens the dashboard, authenticates with their own Google account,
and from that point on *that account* — not a hardcoded one — is what gets
scraped for Naukri notification emails and what sends replies. This is a
multi-user change, not just a UX change: every row, every scrape cycle, and
every send must now be attributed to and scoped by the signed-in identity
that produced it, or one user's data/sends could leak into another's.

ARC-0001 already defined the Gmail Gateway, Persistence Gateway, Ingestion
Path, and Review & Approval Path concepts and the send-gate rule. This ADR
does not change any of those rules — it changes *whose* credential and
*whose* rows each of those concepts operates on, by introducing identity as
a first-class dimension threaded through all of them.

## Decision

1. **Sign-in is the only credential source:** in production, a Google
   identity may only enter the system through the Sign-In Flow (interactive
   OAuth consent completed by that user). No hardcoded/static
   `GOOGLE_CLIENT_ID`/`SECRET`/`REFRESH_TOKEN` triple, and no shared token
   file, may be used to derive the identity used for scraping or sending.
2. **One credential, one user:** the Credential Store holds at most one
   active credential per user identity. A credential obtained for one user
   is never attached to, reused for, or merged with another user's identity.
3. **Every Gmail Gateway call is scoped:** every call into the Gmail Gateway
   (search, read, send) must be made with the credential belonging to a
   specific User Scope — either the current Session's user (Review &
   Approval Path) or the one user the Ingestion Path is currently iterating
   (never a global/default credential).
4. **Every row is scoped:** every row the Persistence Gateway holds (queue
   rows, candidate-digest rows, per ARC-0001) carries the owning User Scope.
   The Ingestion Path writes only to the scope it is currently scraping for;
   the Review & Approval Path reads/writes only the current Session's scope.
   Cross-scope reads or writes are forbidden, including in aggregate/admin
   views unless a future ADR explicitly ratifies one.
5. **Ingestion iterates per user:** the Ingestion Path's scheduled run does
   not fetch for "the" account — it iterates every User Scope with a valid
   Credential Store entry and runs one fetch cycle per user, keeping Gmail
   Gateway calls and Persistence Gateway writes scoped to that iteration's
   user throughout. A failure for one user's pass must not abort or leak
   into another's.
6. **Send-gate applies per user (extends ARC-0001 invariant 1):** a send may
   still only originate from an explicit human action on the Review &
   Approval Path, and it must use the credential of the Session's own user —
   never another user's credential, even if the acting user has access to
   that row through some future shared/admin view.
7. **Revocation ends scraping:** when a user signs out or their Google
   consent is revoked/expired, the Ingestion Path must stop iterating that
   user (skip them on the next run, not error the whole cycle) until they
   complete the Sign-In Flow again. Their existing rows are not deleted.

## Rationale

Hardcoding one credential was fine for a single-user personal tool, but it
means the identity that gets scraped and the identity that sends is a
deployment-time config choice, not a user action — the opposite of "sign in
with Google." Moving credential acquisition into an interactive Sign-In
Flow is the easy part; the invariant that actually prevents data leakage
between users is scoping — every row and every Gmail Gateway call must
carry an explicit User Scope, checked the same way everywhere, rather than
trusting each new code path to remember to filter by user. Iterating the
Ingestion Path per user (invariant 5) instead of adding a "current user"
global keeps the automated path stateless with respect to identity, so a
scheduling bug can't silently scrape or send as the wrong account.

## Consequences

- `PRODUCTION.md`'s OAuth setup (steps 1–3, the static env-var triple) is
  superseded and needs to be rewritten around the Sign-In Flow + Credential
  Store once implemented; the Railway Cron service also needs a way to
  iterate stored users instead of reading one fixed set of env vars.
- The Persistence Gateway's schema must grow to add a User Scope column (or
  equivalent) on every existing table, plus a Credential Store table —
  schema migration work, not an architecture decision, but required before
  this ADR can be implemented. Existing single-account data must be
  backfilled to one User Scope during migration.
- The Review & Approval Path needs session/login infrastructure it doesn't
  currently have (it's presently an unauthenticated local/internal
  dashboard) — adding that is in scope for implementing this ADR.
- The Ingestion Path's `run_fetch()` shape changes from "one fetch cycle"
  to "one fetch cycle per signed-in user"; anything that calls it
  in-process (the dashboard's "Run Email Check Now" button, per ARC-0001)
  must decide whether it means "run for me" (current Session's scope) or
  "run for everyone" and pass that intent explicitly.
- ARC-0001's Field Parser, Classification Gate, and Lifecycle State Machine
  concepts are unaffected in behavior — they simply now operate on rows
  that carry a User Scope, same as everything else in the Persistence
  Gateway.

## Open (not yet ratified — do not implement past this line without a decision)

- Whether the dashboard's own access is still restricted (e.g. an allowlist
  of Google accounts permitted to sign in at all) or open to any Google
  account is undecided.
- Whether/how a signed-in user can see or manage multiple Gmail identities
  of their own (vs. exactly one account per user) is undecided — this ADR
  assumes one identity per signed-in user.
- The mechanics of credential encryption at rest in the Credential Store
  are not specified here — that's an implementation/security decision
  against invariant 2, not a re-opening of it.

## Resolved (post-ratification amendments)

- **External Tracker Record isolation** (was Open, above) — resolved
  2026-09-01, dedicated multi-user security audit: one `tracker.xlsx` per
  user under `TRACKER_DIR/<user_id>.xlsx` (`excel_tracker.py`,
  `upsert_tracker_row(user_id, queue_row)`), never a single shared file.
  The prior shared file commingled every user's subject/company/role/
  hr_email/status with no `user_id` column — not reachable through any
  HTTP route (verified: no route in `app.py` reads, downloads, or serves
  this file), but a real defense-in-depth gap inconsistent with invariant 4
  ("every row is scoped"). Verified by
  `tests/test_multiuser_isolation.py::test_excel_tracker_isolation`,
  confirmed failing against the pre-fix code (`git stash`) and passing
  after (`git stash pop`).
- **Resume isolation** — resolved 2026-09-01, same audit. Resumes are a
  User-Scoped resource under invariant 4 just as queue rows are, but the
  original implementation stored them in one shared `RESUMES_DIR` with no
  per-user separation: `latest_resume()` picked the most-recently-modified
  PDF across *all* users, so any user's outreach could attach any other
  user's resume, and `GET /api/resume` returned it to whoever asked.
  Resolved by scoping to `RESUMES_DIR/<user_id>/` (`_user_resume_dir()`,
  `app.py`) and adding an authenticated `POST /api/resume` upload endpoint
  (no upload path existed before this fix). Verified by
  `tests/test_multiuser_isolation.py::test_resume_isolation` and
  `::test_resume_upload_is_per_user`, same fail-then-pass verification.
