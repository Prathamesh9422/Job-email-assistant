# ARC-0001 — Layered pipeline with a human send-gate

- **Status:** Accepted (architect-ratified)
- **Owner:** @architect
- **Applies to:** `fetch_job.py`, `gmail_client.py`, `db.py`, `app.py` and their callers
- **Supersedes:** —

## Context

This app watches Gmail for Naukri notification emails, lets a human triage and edit
each one in a dashboard, and sends a reply/cold-outreach email with a resume
attached. It runs as two independent processes in production (Railway): a
cron service (`fetch_job.py`, once daily) and a web service (`app.py`, always
on), sharing one Postgres database.

The single highest-consequence failure mode for a tool like this is an
automated process silently emailing real HR contacts — a bad regex match, a
scraper mistake, or a scheduling bug could send an embarrassing or wrong
email with no human ever seeing it first. The codebase already defends
against this structurally (see the `fetch_job.py` docstring and
`PRODUCTION.md`); this ADR ratifies that structure so it isn't accidentally
eroded by a future change, and documents the module boundaries the rest of
the pipeline relies on.

## Decision

1. **Send-gate:** `gmail_client.send_new`, `gmail_client.send_threaded_reply`,
   and `gmail_client.send_new_with_attached_eml` may only be called from an
   `app.py` request handler reached by an explicit user action (the
   dashboard's Approve & Send flow). No code reachable from `fetch_job.py` /
   `run_fetch()` may call them, directly or transitively.
2. **Gmail gateway:** `gmail_client.py` is the only module that talks to the
   Gmail API (auth, search, get, send). No other module constructs Gmail API
   credentials or calls `googleapiclient` directly.
3. **Persistence gateway:** `db.py` is the only module that opens a database
   connection or issues SQL. All other modules (`app.py`, `fetch_job.py`,
   `naukri_parser.py` via its caller) read/write the queue exclusively
   through `db.py`'s public functions, which present the same signatures
   regardless of the SQLite/Postgres backend in use.
4. **Fetch is parse-only:** `fetch_job.py` may search/get Gmail messages and
   parse them (via `naukri_parser.py`) and write rows to `db.py`, but must
   never enrich (`scraper.py`), render (`templates_engine.py`), or send.
   Those steps belong to the human-triggered path in `app.py`.
5. **Tracker is a side-effect of a confirmed outcome:** `excel_tracker.py` is
   written only after `app.py` has confirmed a terminal outcome (sent,
   failed-send, or skipped) for a queue row — never speculatively.

## Rationale

Separating "notice and parse" (cron, automated) from "enrich, render, and
send" (dashboard, human-approved) means the code path that can talk to real
people is small, auditable, and only reachable through one explicit UI
action. Routing all Gmail API and all DB access through two single gateway
modules means the OAuth/credential logic and the SQLite/Postgres portability
logic each exist in exactly one place, instead of being reimplemented or
subtly diverging across callers.

## Consequences

- Any new automated/scheduled entry point (another cron job, a webhook, a
  background worker) must be reviewed against invariant 1 before it's added
  — it inherits the same "no send" constraint as `fetch_job.py` unless this
  ADR is revised.
- Adding a new place that needs Gmail API access or DB access means adding a
  function to `gmail_client.py` / `db.py`, not opening a new client/connection
  inline in the caller.
- `app.py` remains the single place where human approval and sending are
  coupled; splitting the dashboard into multiple services later must
  preserve that coupling or this ADR needs a revision.

## Open (not yet ratified — do not implement past this line without a decision)

- Whether a future "digest" or "batch approve" UI feature may send multiple
  emails from one click is undecided — treat it as still requiring a human
  action per invariant 1, but the UX for batching is not specified here.
- No automated retry-and-send-on-failure path is specified; retries of a
  failed send must still go through the human Approve & Send action.

## Change process

This decision is ratified. Any change to the invariants above requires updating this ADR and
architect sign-off — a developer or agent request alone does **not** authorize it.
