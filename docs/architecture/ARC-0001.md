# ARC-0001 — Layered pipeline with a human send-gate and application lifecycle

- **Status:** Accepted (architect-ratified)
- **Owner:** @architect
- **Applies to:** the Ingestion Path, Gmail Gateway, Persistence Gateway,
  Classification Gate, Lifecycle State Machine, and Review & Approval Path
  concepts defined below, and their callers
- **Supersedes:** —
- **Amended:** added the Classification Gate and Lifecycle State Machine
  concepts and their invariants (6–10 below); original send-gate/layering
  invariants (1–5) unchanged

## Concepts

| Concept | Role |
|---|---|
| **Ingestion Path** | Automated, unattended entry point. Watches the inbox, classifies and parses what it finds, records it. No human in the loop. |
| **Gmail Gateway** | The only thing that speaks to the mailbox — auth, search, read, and send. |
| **Classification Gate** | Looks at one incoming message and decides what kind of thing it is, before anything downstream touches it. |
| **Field Parser** | Given a message and its known type, extracts structured fields. Doesn't decide type, doesn't decide status. |
| **Persistence Gateway** | The only thing that reads or writes durable state. |
| **Lifecycle State Machine** | The only thing that decides whether a status change is legal. |
| **Enrichment** | Looks up missing details (e.g. an HR contact) for a row a human is actively reviewing. Human-triggered. |
| **Rendering** | Turns a row + template into the email a human is about to approve. Human-triggered. |
| **Review & Approval Path** | Where a human looks at a row, edits it, and takes the one action that can produce a real send. |
| **Send Gate** | The rule, not a place: a send may only originate from an explicit human action on the Review & Approval Path. |
| **External Tracker Record** | A record of a *confirmed* outcome, kept in sync after the fact — never a source of truth. |

## Context

This app watches a mailbox for job-site notification emails, lets a human
triage and edit each one in a dashboard, and sends a reply/cold-outreach
email with a resume attached. It runs as two independent processes in
production: an always-off-by-default Ingestion Path (runs on a schedule,
exits) and an always-on Review & Approval Path (the dashboard), sharing one
database.

The single highest-consequence failure mode for a tool like this is an
automated process silently emailing real HR contacts — a bad parse, a bad
lookup, or a scheduling bug could send an embarrassing or wrong email with
no human ever seeing it first. The codebase already defends against this
structurally; this ADR ratifies that structure so it isn't accidentally
eroded by a future change, and documents the boundaries the rest of the
pipeline relies on.

The app's purpose has grown beyond "notice an application and reply once."
The full intent is to track a job application through its **whole
lifecycle**: (1) applied → notification arrives, (2) reply sent to the real
HR contact, (3) HR replies with next steps — selection, rejection, an
interview or walk-in call, (4) one or more interview rounds, (5) final offer
or rejection. The source mailbox also carries messages that are **not**
application notifications at all — recommended/matching-job digests naming
a candidate opportunity the user hasn't applied to yet. Those need the same
HR-contact enrichment as real applications and must be surfaced in the
dashboard as something the user can act on (apply), not silently discarded
or conflated with real applications. Both of these are new classification
and state-tracking concerns layered on top of the existing pipeline, so
this ADR is amended (not superseded) to cover them.

## Decision

1. **Send-gate:** a send may only originate from an explicit human action on
   the Review & Approval Path (the dashboard's Approve & Send flow). Nothing
   reachable from the Ingestion Path may trigger a send, directly or
   transitively.
2. **Gmail gateway:** exactly one component talks to the mailbox provider
   (auth, search, read, send). No other component builds mailbox
   credentials or calls the mailbox API directly.
3. **Persistence gateway:** exactly one component opens a database
   connection or issues SQL. Every other component reads/writes state
   exclusively through its public interface, which behaves identically
   regardless of which database backend is active underneath.
4. **Ingestion is parse-only:** the Ingestion Path may read mailbox messages,
   parse them, and write rows to the Persistence Gateway, but must never
   enrich, render, or send. Those steps belong to the human-triggered
   Review & Approval Path.
5. **Tracker is a side-effect of a confirmed outcome:** the External Tracker
   Record is written only after the Review & Approval Path has confirmed a
   terminal outcome (sent, failed-send, or skipped) for a row — never
   speculatively.
6. **Message classification gate:** every incoming message must be
   classified into exactly one type — application notice, HR reply, or
   candidate digest — before any parsing or persistence happens.
   Classification is a single, testable decision point, not logic scattered
   across the Field Parser or Ingestion Path.
7. **HR replies advance an existing row, they never create one:** a message
   classified as an HR reply must be matched to its existing row (via the
   mailbox thread id) and applied as a lifecycle transition on that row. It
   is a bug, not a feature, for an HR reply to insert a new row.
8. **Lifecycle transitions are centrally validated:** every status
   transition beyond the existing pre-send states (`needs_info → ready →
   sent`) is computed by the Lifecycle State Machine's transition table,
   never written ad hoc by a caller. An illegal transition (e.g.
   `rejected → interview_scheduled`) must be rejected, not silently
   applied. Advancing an interview round increments a round counter on the
   row; it does not invent a new status per round.
9. **Candidate digests are first-class, not discarded:** a message
   classified as a candidate digest is parsed and, once a human runs it
   through Enrichment on the Review & Approval Path (invariant 4 still
   applies — enrichment stays human-triggered, never automatic), presented
   in the dashboard as an actionable "apply" candidate. It is stored as a
   distinct row/status from real applications, never merged into or
   confused with them, and only enters the Lifecycle State Machine
   (invariant 8) once a human applies to it.
10. **Ingestion stays parse+classify-only:** the Ingestion Path may classify
    and parse messages of all three types and write/update rows via the
    Persistence Gateway, but must never enrich, render, or send regardless
    of message type — the send-gate (invariant 1) applies uniformly across
    all three.

## Rationale

Separating "notice and parse" (automated) from "enrich, render, and send"
(human-approved) means the code path that can talk to real people is small,
auditable, and only reachable through one explicit UI action. Routing all
mailbox access and all persistence through two single gateways means the
credential logic and the storage-backend logic each exist in exactly one
place, instead of being reimplemented or subtly diverging across callers.

Classifying every message once, in one place, before anything else happens
avoids the alternative — parsing logic guessing at message intent via ad
hoc heuristics scattered across call sites, which is exactly how an HR
reply could get misparsed as a new application, or a candidate digest
silently dropped. Centralizing lifecycle transitions in one state machine
avoids the equivalent failure mode for status: without a single transition
table, it becomes easy for one code path to move a row from `rejected` back
to `interview_scheduled`, or to invent a slightly different status string
per interview round, silently fragmenting the data the dashboard and the
External Tracker Record depend on.

## Consequences

- Any new automated/scheduled entry point (another cron job, a webhook, a
  background worker) is part of the Ingestion Path concept and must be
  reviewed against invariant 1 before it's added — it inherits the same
  "no send" constraint unless this ADR is revised.
- Adding a new place that needs mailbox access or persistence means
  extending the Gmail Gateway / Persistence Gateway, not opening a new
  client/connection inline in the caller.
- The Review & Approval Path remains the single place where human approval
  and sending are coupled; splitting it into multiple services later must
  preserve that coupling or this ADR needs a revision.
- The Field Parser gains a required upstream step (the Classification Gate)
  it did not previously have; any caller that fed it a raw message directly
  must be updated to classify first.
- The Persistence Gateway's schema must grow to represent lifecycle state
  (interview round counter, HR-reply-derived timestamps, a distinct
  row/status for candidate opportunities) — a schema migration, not an
  architecture decision, but one this ADR now requires exist.
- Existing rows created before this amendment won't have classification or
  lifecycle history; treat them as starting in whatever their current
  status implies and let new transitions take over from there.

## Open (not yet ratified — do not implement past this line without a decision)

- Whether a future "digest" or "batch approve" UI feature may send multiple
  emails from one click is undecided — treat it as still requiring a human
  action per invariant 1, but the UX for batching is not specified here.
- No automated retry-and-send-on-failure path is specified; retries of a
  failed send must still go through the human Approve & Send action.
- The exact set of lifecycle statuses/round-numbering scheme and the HR-reply
  classification heuristic (rule-based vs. something fuzzier) are not
  specified here — that's implementation detail for the Lifecycle State
  Machine and Classification Gate to work out against this ADR's
  invariants, not a re-opening of the invariants themselves.
- Whether a candidate-digest row and an application-notice row share one
  table (distinguished by a status/type column) or live in separate tables
  is undecided; either satisfies invariant 9 as long as they remain
  distinguishable and never merge silently.

## Change process

This decision is ratified. Any change to the invariants above requires updating this ADR and
architect sign-off — a developer or agent request alone does **not** authorize it.
